## 2. Fold counters in the layer (graph safety)

**Allocation.**
- `_K1_CNT[dev] = torch.zeros(1 << 16, int32)` is created on the first eager K1 call. In practice that is the first
  self-test call in `prepare()`.
- `_k1_prepare` asserts that it exists, inside the `try` that prints `[k3] K1 constants FAILED`. So the buffer
  exists even with `K1_SELF_TEST = False`.
- Its size is a constant (shape-only). Nothing about it depends on input values.

**Use.**
- Every K1 call passes the same buffer. The fold kernel's last CTA per (b, head pair) resets the counter it
  incremented. A request with a single split never touches its counter.
- If the counters were missing under capture, `_k1_ready` would send the call to r1. `_k1_run` itself raises in that
  case, and kernel_fn's catch-and-disable logs `[k3] K1 raised at call time`.

**Why it is graph-safe.**
- The pointer is baked into each captured graph, and the buffer lives for the whole process.
- K1 runs only on the main stream. The side stream (router) starts after K1, so two K1 launches are never in flight
  together.
- Every graph replay starts from all-zero counters.

**Self-test.**
- The 11 k1_v1 cases each run fold, then separate, then fold. The second fold run proves that the first one left
  the counters at zero.
- After every call it checks `int(cnt.abs().sum()) == 0` and prints `counters 0` or `counters NOT RESET`.
- Any failure prints exactly one `[k3] K1 self-test FAILED: attention stays on the r1 FA3 path` and puts all
  attention on r1.

**Gating scope (deliberate).** The self-test includes the 6 L=8 cases, so an L=8 failure would also turn off L=1,
even though L=8 is not routed. Those cases passed on the GPU twice (jobs d857095aa064476f and f7843f722b124e77,
`counters 0` on every line). Prepare time on the GPU is about 0.8 s.

## 5. Risks

1. **The self-test gates all of K1** (§2). An L=8 self-test failure on the GPU would cost the L=1 wins too. It
   passed twice on the judge.
2. **Fold counters are one per device.** Two K1 launches in flight on different streams would race. This does not
   happen in the judge's flow (K1 runs only on the main stream, and graphs replay sequentially). A kernel that died
   mid-flight would leave counters set, but that is a sticky device fault anyway.
3. **The import-time nvcc** for k1_v1 took 42 s standalone (35 s for v0 in the layer). Prepare adds about 1 s of
   self-test. Both are well inside budget with K2A off.
4. **The in-situ gain may differ from standalone.** The fold path's last-CTA merge adds about 0.7 µs per
   (b, head pair) tail. At dec1 full the separate combine (5.9 µs standalone) is a second launch inside the layer
   graph.
5. **Unrouted / not validated here:**
   - `R1_LOCAL_ID_TABLE = False` and `USE_K2A = True` at T = 65–192 are unchanged v04 code.
   - The k2a_switch scenario only checks that K2A still builds and self-tests behind its switch.
