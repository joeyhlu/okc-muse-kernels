# K1 v4 (`k1_v4.py`, nonce k1-v4-1): box results, 2026-10-24

Everything below was measured on the box H200 (the judge's image) and run through `box.sh timed`. The logs are in
`box_out/k1v4_*`. Only same-process A/Bs and the judge clone's paired ratios are used as evidence, because single
bench numbers drift by up to 20 % when the GPU is shared.

**Outcome.**
- **Item 2 (merge) is kept.** The fold merge now keeps 8–16 partial loads in flight per thread. Judge ×3 against
  k1_v2 in the same session: **1.4757 vs 1.4126 (+4.5 %)**. Sliding L=1 gains 4–10 % and full B16 / B32 L=1 gain
  8–15 %.
- **Item 1 (L=8 FP16 QK) is killed.** The kernel is correct but lands at ver32 full 442 µs and ver16 full 236 µs. The
  bar was ≤ 330 / ≤ 170, and rung-1 does 382 / 197. The L=8 kernel stays in the file, compiled, self-tested and
  unrouted.
- **Routing is unchanged from k1_v2:** K1 for L=1 at every batch size; the rung-1 FA3 path (with L2) for L=8.

| reader | 1 load in flight / thread | 4 | 8 |
|---|---|---|---|
| 256 threads | 3.20 µs (20 GB/s) | 1.18 µs (55) | 1.12 µs (59) |
| 1024 threads | 0.93 µs (71) | 0.58 µs (114) | |

What the lab shows:
- **Freshness is not the problem.** Reading data just written by other SMs is as fast as reading it from a later
  kernel.
- **Fences and load flavour don't matter.** Only acquire loads are slow.
- **The rate is set by loads in flight (MLP).** The v1–v3 merge had about one dependent L2 round trip per split.
- **Verdict:** a mode reaches ≥ 100 GB/s once there is enough MLP (186–195 GB/s at 1024-thread-equivalent depth), so
  the merge fix is kept.

The fix is in `merge_finalize`. It makes one pass with an online max over batches of UN splits: UN = 16 at L=1 and
8 at L=8. All UN lse values and float4 partials of a batch are issued before any of them is used, and the gate
values are loaded up front.

k1_v2 scores 1.347.

Per-shape changes, all from the merge:
- **sliding L=1:** +4–10 %.
- **full B16 / B32 L=1:** +8.4 % and +15.5 % (112 → 103 µs and 230 → 199.5 µs). Those shapes use the in-kernel fold.
  Their last-CTA merges (S = 16 / 8) used to make dependent L2 round trips while the other ~260 CTAs were saturating
  memory. Under that load each round trip costs ~1.5–2 µs, so the old merge put ~25 µs on the critical path.
- **L=8 shapes:** unchanged (rung-1).
- **dec1 full:** 0.987× (22.36 → 22.6 µs), consistent across all 3 runs. This shape uses the separate

  moves two loads above the page-table/cp.async chain at L=1 and lengthens register live ranges. A second candidate is
  the inlined 16-deep merge (95 → 109 registers). It costs −0.6 % on the decode-1 load, against +5.6 % from dec1
  sliding. Next burst: drop the hoist at L=1 first, then try UN=8 / a non-inlined merge.

The full B16 / B32 gain rests on the three paired judge runs above. The k1_v3 sweep1 bench reading of 91 / 207 µs was
environmental: its separate-combine variant, with no merge at all, was just as fast. That reading is not evidence for
or against the merge.

## 3. L=8 with FP16 QK from a once-converted K tile (item 1): killed

### Design

1. Warp = (KV head, 16-row m-tile), covering all keys.
2. Each loader thread converts its own two K chunks and two V chunks of every tile to FP16 (exact) into single
   16 KB `Kh` / `Vh` tiles. The tile layout is: key row 256 B, chunk `c16 ^ (x&7) ^ 2h`.
3. Each tile needs two barriers:
   - A: the previous tile has been consumed.
   - B: the conversion has finished.
4. QK runs as `ldmatrix.x4` (non-trans) + m16n8k16 FP16, with FP16 Q A-fragments.
5. PV runs as `ldmatrix.x4.trans` + m16n8k16.

**Shared memory:**
- ring: ST × 16 KB;
- `Kh` + `Vh`: 32 KB;
- FP16 Q staging: 16 KB, aliased onto `Kh`/`Vh`, because Q goes into registers before the first conversion;
- new-token tile: 4 KB;
- cos/sin: 2 KB.

That totals 102 KB at ST=4, which allows 2 CTAs/SM.

**Registers:** at most 128 (16 B of spills) once each 64-key tile is processed as two 32-key halves. The first
version used whole tiles and spilled 88 B.

### Correctness

- The self-test passes, comparing against the FP32 / BF16-query reference.
- Every bench variant passes `check_implementation`.
- `k1_v4_emulate.py` passes:
  - a new test for the FP16 K tile, the `ldmatrix` non-trans QK fragments, the Q A-fragments and bank conflicts;
  - all 21 end-to-end cases with FP16 L=8 queries (tight check about 0.5 % against the BF16-query reference).
- `k1_emulate.py` and `k1_v3_emulate.py` are unchanged in behaviour: the new `L8_Q_FP16` switch defaults to off.
  `k1_emulate.py` still passes 21/21.

### Why it loses

These are measured constants plus counts, not a profiler.

**Instruction count.** Per key, both heads × 64 rows need:
- 8 HMMA.16816 (QK 4, PV 4);
- 128 exp2.

**Throughput floors**, from the lab rates (HMMA ≈ 0.5–0.67/clk/SM, MUFU 16/clk/SM):

| pipe | floor |
|---|---|
| HMMA | 12–16 clk/key |
| MUFU | 8 clk/key |
| memory (bare stream, 3.4 TB/s) | ~20 clk/key |

**Measured:** ~45 clk/key, i.e. B32 full at 442 µs.
- The pure stream alone is 193 µs.
- In v3, removing QK alone took B32 from 433 to 222 µs. With PV and softmax present, removing QK removes nearly all
  the compute time.
- Moving QK to native FP16 HMMA from a shared K tile did not make it cheaper than v3's emulated FP8 QK.

**What that means.** The tile cost is a dependency/latency chain at 16 warps/SM with one or two CTA barriers per
64 keys:

`ldmatrix → 4 dependent k-steps → 16-deep max + 2 shuffles → exp2 → pack → 4-deep PV chains`

No single pipe is saturated.

**What would remove the barriers** (double-buffered `Kh`/`Vh`, two tiles per barrier, or warp-specialized
producers) needs 32–64 KB more shared memory. That costs the second CTA/SM, and in v3 the one-CTA build was worse
(500+ µs). Register room is also exhausted (128 at 2 CTAs/SM). On H100 an mma.sync design for 128 rows × 64 keys
per CTA has no headroom left.

**The structural fix is wgmma** (item 4):
- 64-row warpgroup tiles with B from shared memory;
- native FP8 QK and PV, so no conversion step;
- accumulators that don't compete with a per-warp softmax chain.


- **Cache layout.** The kernel reads the FP8 page-1 cache in exactly SGLang's layout: rows of `Hkv × 64` e4m3, page
  table → row. It gathers both KV heads of a row as one 128 B segment, where FA3 fetches two 64 B halves.
- **Graph capture.** Fixed grids; per-request lengths are read on device; no host syncs.
- **Prepare-time state:**
  - the `inv_freq` table.

## 4. compute-sanitizer

`k1_v3_san.py --file k1_v4.py` covers sliding L=1 B=3 ctx 2047 page 1, and full L=8 B=2 ctx 3000 page 1 soft.
Each runs `_k1` fold, `_k1` separate, and the routed `kernel_fn`, which includes the 11-case self-test exercising
both K1 kernels (box_out/k1v4_san_mem.log, k1v4_san_race.log).
- **memcheck: 0 errors.** All six outputs pass `check_implementation`.
  - The L=8 K1 kernel with FP16 Q sits at 0.48 % relative L2.
  - The routed FA3 path with E4M3 Q sits at 6.7 %.
- **racecheck: 0 hazards in any `k1::` kernel.** That includes the two-barrier K/V conversion of the L=8 kernel and
  the new merge.
- The single reported hazard is inside SGLang's stock FA3 kernel (the routed L=8 path), the same as in k1_v3.
