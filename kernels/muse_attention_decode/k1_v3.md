# K1 v3 (`k1_v3.py`, nonce k1-v3-1): box results, 2026-10-24

Everything below was measured on the rented H200 running the judge's image. Two tools were used:
- the judge clone (`tools/judge/judge.py`, paired against SGLang, cold L2);
- `k1_v3_bench.py`, which follows judge-style rules: CUDA graph, cold L2 before every replay, the empty-graph cost
  subtracted, and `check_implementation` run on every variant.

From the coordinator's message onwards, a second agent shared the GPU. Bench µs drifted by up to about 20 % between
runs (full B16 L=1 read 114.6, then 91.0, then 114.7 µs). Only variants measured in the same process should be
compared. The judge ratios are paired, so the drift cancels in them.

**Outcome.** The kill criterion was hit for goal 1. The L=8 kernel was rewritten as the brief describes. It is
correct, but it is slower than the rung-1 path at every L=8 shape, so it is **not routed**. Routing is the same as
k1_v2: K1 for L=1, and the rung-1 FA3 path with L2 for L=8. The problem speedup on the box is unchanged.

## 2. L=8 kernel v3 (goal 1): the design and why it loses

**Design.**
- Warp = (KV head, 16-row m-tile: 2 tokens × 8 q heads), covering all 64 keys of a tile. 2 CTAs/SM.
- V is converted ONCE per tile. Each loader thread converts its own two cp.async chunks right after its
  `wait_group`, so no extra barrier is needed. They go into a double-buffered fp16 smem tile, with swizzle
  `c16 ^ (x&7) ^ 2h`.
- PV uses `ldmatrix.x4.trans` + `m16n8k16` FP16.
- QK uses `m16n8k32.e4m3` on the raw K bytes, with Q as E4M3.

**Correctness.**
- Self-test passes.
- All judge checks pass in every bench.
- `k1_v3_emulate.py` passes:
  - a new fragment, bank and STS test for the fp16 V tile and ldmatrix.trans;
  - all 21 k1_emulate cases with the v3 L=8 warp roles;
  - `k1_emulate.py` itself is unchanged and still passes.

Bench, same process (box_out/k1v3_sweep2.log / sweep3; µs):

| shape | v3 L=8 | rung-1 | v1 L=8 (judge, d857) |
|---|---|---|---|
| ver1 sliding | 40.6 | 18.3 | 42.8 |
| ver16 sliding | 39.6 | 24.6 | 43.8 |
| ver32 sliding | 42.2 | 30.5 | 46.9 |
| ver1 full | 35.1 | 31.6 | 39.4 |
| ver16 full | 238.8 | 195.1 | 265.5 |
| ver32 full | 454.4 | 384.8 | 497.0 |

Measured findings:

1. **`mma.sync.m16n8k32.e4m3` is emulated on sm_90.** The SASS of `k1_main<8,4>` has no QMMA. Each FP8 mma
   becomes `F2FP.F16.E4M3.UNPACK_B` conversions plus 2 × `HMMA.16816.F32`. So the "FP8 QK" lever of v1/v2 never
   halved the tensor work. It also means each of the 4 m-tile warps unpacks the same K bytes (64 F2FP per warp per
   tile). Any FP8 mma.sync plan on H100/H200 is FP16 HMMA in disguise; only wgmma has native FP8.
2. **Isolation builds (`K1_DIAG`, box_out/k1v3_diag34.txt) at B32 full L=8.** All in µs; same-session numbers with
   possible co-tenant noise.

   | build | µs | note |
   |---|---|---|
   | full kernel | 428–454 | |
   | no PV mma (D1) | 427 | no change |
   | no exp2 for P (D2) | 428 | no change |
   | no tile compute, conversion kept (D3) | 220 | |
   | no compute, no conversion (D4) | 193 | 3.4 TB/s, the bare 2-CTA × 4-stage cp.async pipeline |

   Removing either the PV HMMAs or the MUFU work alone changes nothing. The per-tile cost is a latency/dependency
   chain, not one saturated pipe:
   - each warp runs LDS → F2FP → 2 HMMA → 16-deep FMNMX + 2 SHFL → ex2 → pack → 4-deep HMMA chains;
   - there are only 4 warps per SMSP;
   - a CTA-wide barrier comes every 64 keys.

   The conversion step on its own costs about 27 µs at B32: it sits between `wait_group` and the barrier.

   **D5 found the cost: the emulated e4m3 QK is the whole L=8 compute cost.** D5 skips only the QK mma and keeps
   K loads, conversion, softmax and PV (box_out/k1v3_final_batch.txt, same session):

   | shape | default | D5 |
   |---|---|---|
   | B16 full L=8 | 228 µs | 123 µs |
   | B32 full L=8 | 433 µs | 222 µs |

   D5 lands at the D3 level (no compute at all: 220 µs). PV HMMAs, exp2 and the softmax are hidden behind the
   memory stream. The emulated `m16n8k32.e4m3` is not: per warp it does LDS → 8 × F2FP unpack → 2 HMMA per
   n-tile, with the same K bytes unpacked by all 4 m-tile warps.
3. **Per-SM pipe rates** (lab `k1_v3_lab_mb.py`, one wave, 1024 thr/SM):

   | instruction | rate |
   |---|---|
   | ex2.f32 | 16 /clk/SM |
   | ex2.f16x2 | 8 /clk/SM, i.e. 16 values/clk: no gain |
   | cvt.f16x2.e4m3x2 | 53 /clk/SM, i.e. 106 values/clk: cheap |
   | cvt.f16x2.f32 pack | 64 /clk/SM |
   | FMNMX | 64 /clk/SM |
   | PRMT | 64 /clk/SM |
   | HMMA.16816 f32 | ~0.5–0.67 /clk/SM, i.e. ~530–700 TFLOPS |

   The e4m3 mma row of that lab is invalid: it is the emulated sequence above, and its regs limited co-residency.
   - At L=8 the work is 128 ex2 per key, giving an 8 clk/key MUFU floor.
   - It is also 8 HMMA per key (QK 4 + PV 4), about 12 clk/key at 0.67/clk.
   - The memory budget at 3.6 TB/s is ~19 clk/key.
   - So mma.sync L=8 can approach memory speed only with near-perfect overlap. FA2-class efficiency would put it at
     ~26 clk/key, about 270 µs at B32, still a 1.4× win over rung-1 — but the v3 structure reaches only ~42
     clk/key.
4. **Per-CTA phase stamps** (`K1_PROF` %globaltimer, box_out/k1v3_sweep1/2.log, prof3). All in µs from kernel
   start.

   | phase | ver1 sliding (8 CTAs × 4 tiles) | dec1 sliding L=1 (16 CTAs × 2 tiles) |
   |---|---|---|
   | plan | 1.5 | 1.5 |
   | Q prep + new tokens + prologue loads | 7.2 med / 10.2 max | 4.1 / 5.1 |
   | 4 tiles (L=8) / 2 tiles (L=1) | 13.8 / 17.4 | 5.6 / 6.4 |
   | epilogue + partials | 21.3 (last arrival) | 9.7 |
   | last-CTA merge | 40.7 | 13.8 |

   **L=8 last-CTA merge: ~19 µs.**
   - Sub-stamps: lse staging 1.8 µs, weights 1.8 µs, then ~15 µs until every warp has finished summing 8 splits ×
     128 rows × 256 B (256 KB).
   - That is ~17 GB/s for one CTA: latency-bound reads of partials just written by other SMs.
   - The v3 changes did not move it: the staged merge with independent loads, hoisted gate loads, and the gate L2
     prefetch.

   **L=1 last-CTA merge: 4.1 µs** for 16 splits × 16 rows (64 KB), the same ~20 GB/s. **This is the main remaining
   latency in the sliding L=1 shapes** (goal 3).

**Kill decision.** At ~2 h, L=8 v3 lost to rung-1 on all six verify shapes, so v3 ships goals (2)–(3) tuning only,
and L=8 stays on rung-1. The v3 L=8 kernel is kept in the file: compiled, self-tested, sanitizer-clean and unrouted.

## 3. Goals 2–3: what the sweeps said (route/tuning tables in the file)

All in-process bench comparisons:
- **Ring depth** (`K1_STAGES_T`, template, L=1 {4, 6}). 6 stages measured 14.5 / 24.9 / 17.5 / 116.1 / 20.9 /
  232.4 µs against 4 stages at 14.7 / 23.8 / 16.9 / 114.6 / 20.6 / 230.0 µs. More in-flight bytes do not help L=1
  full; the bare pipeline already gives 3.4 TB/s (D4), so the L=1 full gap to it (230 vs 193 µs at B32) is
  compute/epilogue, not depth. Kept at 4.
- **Sliding L=1 tunables.** `min_chunk` 1 was worse at B1 (17.0 vs 14.6 µs). cps 2 was worse at B16 (19.1 vs
  17.0 µs). Kept k1_v2's values (2, 1).
- **Full B1 L=1.**
  - fold instead of `k1_combine`: 53–63 µs against 23.8 µs.
  - `min_chunk` 4: 24.0 µs.
  - `min_chunk` 8: 26.6 µs.
  - Kept separate combine, `min_chunk` 2.
- **Full B16/B32 L=1.**
  - `min_chunk` 4: same.
  - separate combine: +1.4 / +3.7 µs.
  - Kept fold.
- **Sliding L=8** `min_chunk` 1/2 and cps 1: no gain, because the merge dominates.

## 4. compute-sanitizer (box_out/k1v3_san_mem.log, k1v3_san_race.log)

`k1_v3_san.py` covers sliding L=1 B=3 ctx 2047 page 1, and full L=8 B=2 ctx 3000 page 1 soft. Each runs
`_k1` fold, `_k1` separate, and the routed `kernel_fn`, which includes the 11-case self-test that exercises both K1
kernels.
- **memcheck: 0 errors.** All six outputs pass `check_implementation`.
- **racecheck: 0 hazards in any `k1::` kernel.** That includes the barrier-free per-thread V conversion of the L=8
  kernel.
- The single reported hazard is inside SGLang's FA3 kernel (`FlashAttnFwdSm90`, the routed L=8 rung-1 path), which
  is stock code.

## 6. Next GPU burst (one batched run each; expected gain)

1. **Last-CTA merge → a distributed merge** (sliding L=1 is weight 46).
   - Every CTA of a request already holds its own O/l. Replace "the last CTA reads all S partials" with a
     two-level split: the last CTA of each group of 4 merges 4, then the last group merges the S/4 group results.
   - Alternatively, spread the merge over all splits: each split finalizes 16L/S rows after a grid-scoped arrival
     counter.
   - Expected: dec1 sliding 14.0 → ~11 µs (merge 4.1 → ~1 µs), dec16/32 sliding −1 µs, which is +6–8 % on the
     decode-1 load. For L=8 sliding, merge 19 → ~3 µs, which makes v3 L=8 ≈ 24/23/26 µs: a win over rung-1 at B16
     (24.6) and B32 (30.5).
   - `min_chunk` 4/8 on dec1 sliding (fewer splits to merge) was tried: 15.1 / 18.2 µs against 14.2 µs, so it is
     worse.
   - First measure *why* one CTA reads L2 partials at ~20 GB/s. A 10-line lab: one CTA reading 256 KB just
     written by 8 other CTAs, `ld.cg` vs `ld.relaxed.gpu` vs `ld.volatile`.
2. **(Now first priority, after D5.) L=8 QK in FP16 from a once-converted K tile**, converted by the loader threads
   exactly like V, with the B fragments via `ldmatrix` (non-trans) and Q in fp16 A-fragments (finer than E4M3).
   - Smem: the extra fp16 K tile can share the V double buffer if ST=3 (48 + 64 + 12 KB ≈ 124 KB). Otherwise use
     single buffers + 1 extra barrier to keep 2 CTAs/SM.
   - Registers: qf grows 8 → 16, which needs a check against the 128 cap.
   - Expected: D5 bounds it at ~222 µs for B32 and ~123 µs for B16. With PV-like QK cost (D1 showed PV ≈ free),
     the realistic range is full B32 L=8 ~240–280 µs vs rung-1 382 (1.35–1.6×) and B16 ~130–150 vs 196.
   - That moves the verify 16/32 loads by +25–35 %, roughly +8–10 % on the problem. Sliding L=8 additionally needs
     item 1's merge fix.
3. **Barrier-light L=8 schedule.** Two tiles per barrier, plus QK of tile i+1 issued before the softmax of tile i
   (FA2-style software pipelining in registers, with the 128-reg cap respected by NT=4 halves). Expected: ~30 % off
   the L=8 tile cost. Combined with item 2, that targets full B32 L=8 ≈ 280–300 µs against rung-1's 382, i.e.
   1.3×.
4. **The real fix for L=8 is wgmma** (native FP8 QK and PV, like FA3), keeping K1's 128 B rows and fused epilogue.
   This is a multi-day item, not a burst.
