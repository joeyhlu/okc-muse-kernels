# K2A v3.5 (experiment, NOT shipped): lossless 5-bit block scales, and where the SM clock drop comes from (2026-10-24)

File: `k2a_v35.py` (`# nonce k2a-v35-1`) = v3.4 + 5-bit scale stages (switch `V3_SCALE5`, now False) + clock probes.

## 1. What lowers the SM clock: the tensor cores, not the decode (`box_out/k35_clock1.log`, K1 alone, v3.3 plan)

| K1 consumer | bs16 µs | bs16 MHz | bs32 µs | bs32 MHz |
|---|---|---|---|---|
| math off | 65.8 | 1978 | 85.3 | 1979 |
| decode half the words + scale, no mma | 69.2 | 1977 | 89.8 | 1978 |
| decode all + scale, no mma | 72.4 | 1971 | 92.9 | 1974 |
| mma on raw words, no decode | 70.0 | **1794** | 89.6 | **1797** |
| decode + mma (sink) | 70.4 | 1787 | 90.6 | 1773 |
| real | 71.8 | 1792 | 92.7 | 1778 |

- Decode never moves the clock (1971–1978 MHz). Any mma.sync stream drops it to ~1790 MHz (−9.3%).
- At bs1–32 most of each m16n8k16's 8 token columns are empty, but tensor energy is per instruction; with mma.sync
  (or wgmma, n ≥ 8) there is no way to issue fewer tensor ops per weight byte than 4 HMMA per 16 B.
- A CUDA-core FP32 path for 1–2-token chunks (no tensor ops) needs ~2.3× the ALU work per kb and would be
  issue-bound (~99% of issue slots at the target rate) — not built.
- So "lower-power decode" has nothing to win: decode is not what throttles.

## 2. Lossless 5-bit block scales (`box_out/k35_lab1.log`)
- Re-encoded scale bytes b' span 116..150 (entropy 3.71 bits; same on another weight seed). Per (matrix, expert),
  codes c = b' - base with base = max(min, max - 31); lossless whenever max - min ≤ 31: **59 of 64** matrices on the
  judge's weight seed (the other 5 keep plain scales; per-matrix format flag + per-matrix bf16 constant).
- Layout per lane per stage: one u32 of 8 nibbles + one byte of high bits; stage 17664 B instead of 18432 (−4.2%).
  Decode: `c = ((nw >> 4q) & 15) | (((hb >> q) & 1) << 4); scale = c * 0x00100010 + K` (~5 ops vs PRMT + IMAD).
- Correct at bs 1/8/16/32/48/40s/128s/257 (rel-L2 3.74–3.77e-3).
- **Slower**: vs v3.3, 5-bit 0.947–0.993 (bs1 −2..−5%, bs8 −2..−3%, bs16 −2..−3%, bs32 −3..−4.5%, bs128/256 −1..−4%).
  The same build with plain scales is 0.97–1.00 (code growth: the cold variant went 71 → 84 regs), so the 5-bit
  extraction itself costs ~2% more than the 4.2% of bytes it saves: the consumer is partly issue-bound
  (decode-only already costs +10% time at full clock above).
- 4-bit codes don't work: the best 16-value window covers 98.7% of scales, so every stage would need escapes.
